# ShipKit 사용자 가이드

ShipKit 은 바뀐 파일만 모아 서버 경로에 맞게 정리한 **패키지**를 만들고, 서버에서 **백업 → 반영 → (필요하면) 되돌리기**를 명령 한 줄로 하는 배포 도구입니다. 빌드(컴파일)는 하지 않으니, 빌드가 필요한 프로젝트는 빌드를 끝낸 뒤 쓰세요.

이 문서는 화면 프로그램(`ShipKit.exe`) 기준입니다. 명령어 버전과 설정 파일의 전체 항목은 README 에 있습니다.

## 1. 설치와 첫 실행

`ShipKit.exe` 를 원하는 폴더(예: `C:\Tools\ShipKit`)에 두고 더블클릭하면 됩니다. 설치 과정은 없습니다.

처음 실행하면 안내 창이 세 단계로 설정을 도와줍니다. 모두 나중에 바꿀 수 있습니다.

| 단계 | 할 일 |
|---|---|
| **연결** | GitLab 주소와 토큰을 넣고 **연결 확인**을 누릅니다. 토큰은 GitLab 오른쪽 위 프로필 → Preferences → Access tokens 에서 `read_api` 권한만 체크해 만듭니다. GitLab 을 쓰지 않으면(git 커밋이나 파일 목록으로만 배포) 아래 체크박스를 켜고 건너뜁니다. GitHub 는 나중에 [연결] 메뉴에서 추가합니다. |
| **패키지 위치** | 패키지를 만들 폴더입니다. 배포할 때마다 이 아래에 프로젝트별·날짜별 폴더가 생깁니다. `{project}` 는 프로젝트 이름으로 바뀝니다. 예: `D:/deploy/{project}` → `D:/deploy/erp/2026-10-29-1140` |
| **프로젝트** | 로컬 git 저장소 폴더를 고르면 이름·프리셋·GitLab 프로젝트를 알아서 채웁니다. **서버 배포 경로**(서버에서 이 프로젝트가 있는 폴더, 예: `/app/tomcat/webapps/ROOT`)만 넣으면 됩니다. 반영 규칙 같은 자세한 설정은 나중에 [프로젝트] 메뉴에서 바꿉니다. |

기존 배포 툴(compiled-java-deployer)을 쓰던 PC 라면 첫 단계에 **가져오기** 카드가 보입니다. 프로젝트와 GitLab 주소를 그대로 가져오고, 토큰만 다시 넣으면 됩니다. 서버 경로가 `D:/…` 같은 Windows 경로인 프로젝트는 Windows 서버로 등록됩니다.

## 2. 화면 구성

왼쪽 위 **작업할 프로젝트**에서 프로젝트를 고르면 모든 메뉴가 그 프로젝트 기준으로 바뀝니다.

| 메뉴 | 하는 일 |
|---|---|
| **배포** | 고르기 → 확인 → 완료 세 단계로 패키지를 만들고, 서버에 올려 반영합니다. |
| **기록** | 만든 패키지 목록. 다시 만들기, 서버 반영 이력, 서버 상태, 서버에서 되돌리기. |
| **프로젝트** | 경로·규칙·서버 명령·제외·서버 연결 등 프로젝트 설정. |
| **연결** | GitLab·GitHub 주소와 토큰. |
| **앱 설정** | 테마, 패키지 기본값, 설정 파일 위치, 처음 실행 안내 다시 보기. |

GitLab 조회나 패키지 생성, 서버 반영 중에도 창이 멈추지 않습니다.

## 3. 배포

제목 아래에 지금 프로젝트의 배포 방식과 서버 경로가 보입니다.

### 시작 전 점검

화면 위쪽 띠에서 배포 전에 걸리는 것들을 미리 확인합니다. 배지에 마우스를 올리면 설명이 보이고, **다시 점검**으로 새로 확인합니다.

| 배지 | 뜻 |
|---|---|
| 브랜치 이름 / 원격과 같음 | 지금 체크아웃된 브랜치와 원격 상태 |
| 원격보다 N커밋 뒤처짐 | 옆의 **pull 받기**로 받을 수 있습니다. fast-forward 만 하고 merge 는 하지 않으며, 받을 파일이 로컬 수정과 겹치면 아무것도 바꾸지 않고 멈춥니다. 받은 뒤에는 다시 빌드하고 미리보기를 하세요. |
| 커밋 안 된 수정 N개 | 테스트용 설정 등이 운영에 섞일 수 있습니다. 배포 파일에 포함되면 확인 단계에서 경고가 됩니다. |
| 빌드 결과 없음 / 폴더 없음 | 먼저 빌드하세요. |
| GitLab 토큰 없음 | [연결] 메뉴에서 토큰을 저장해야 MR 목록을 불러옵니다. GitHub 는 토큰 없이도 공개 저장소는 조회됩니다. |

### ① 고르기

무엇을 배포할지 고릅니다. 탭은 프로젝트에 따라 보이는 것만 나옵니다.

- **MR / PR**: **목록 불러오기**를 누르고 체크합니다. 상태(머지됨·열림·닫힘·전체)와 제목 검색으로 좁힐 수 있고, 목록에 없는 번호는 오른쪽 칸에 띄어쓰기로 적습니다(예: `612 615`). 여러 개를 고르면 머지된 순서대로 합칩니다.
- **git 범위**: 두 커밋(또는 태그) 사이에 바뀐 파일을 배포합니다. 기본값은 가장 최근 태그부터 지금(HEAD)까지입니다. 예: `v1.2..HEAD`
- **파일 목록**: 한 줄에 경로 하나씩 붙여넣습니다. `git diff --name-status` 결과도 그대로 됩니다(`D<TAB>경로` 는 삭제, `R100<TAB>이전<TAB>새` 는 이름변경).
- **빌드 결과 전체** (sync 방식 프로젝트만): 빌드 결과 폴더 전체를 패키지에 담습니다. 서버에서는 내용이 다른 파일만 반영하고, 이번 빌드에 없는 옛 파일은 정리 폴더에서 지웁니다.

**압축 파일도 만들기**를 켜면 패키지 폴더와 함께 `.tar.gz`(Windows 서버는 `.zip`)도 만듭니다. tar.gz 에는 실행 권한이 들어 있어 서버에서 `chmod` 없이 바로 실행할 수 있습니다.

### ② 확인

반영·삭제될 파일과 결과(성공·경고·실패·제외)를 봅니다. 위의 필터 버튼으로 종류별로만 볼 수 있습니다.

- **실패 항목이 하나라도 있으면 패키지를 만들지 않습니다.** 빌드 누락 같은 문제가 있는 채로 일부만 배포되는 사고를 막기 위해서입니다. 실패 항목을 빼고 나머지로 만들지 묻는 창에서 [예]를 누르면 빼고 만듭니다. **경고도 실패로 처리**를 켜면 경고도 같은 취급입니다.
- 경고는 패키지를 막지 않지만 꼭 읽어 보세요. 자주 나오는 경고:
  - 소스가 클래스 파일(빌드 결과)보다 최신 → 빌드 누락 의심
  - 배포 파일에 커밋되지 않은 로컬 수정이 있음
  - git 범위의 끝과 지금 브랜치가 다름 → 복사되는 파일은 지금 작업 폴더의 파일입니다
  - MR/PR 의 커밋이 로컬 저장소에 없음 → pull 이 필요합니다
  - 서버 명령(hooks)이 지난 패키지 때와 다름 → 누군가 `.shipkit.yml` 을 고쳤을 때. 무엇이 추가·삭제됐는지 보여 줍니다
- **알림**은 패키지 밖에서 따로 할 일입니다. 의존성 파일(`pom.xml`, `package.json`, `requirements.txt` 등), DB 마이그레이션, SQL 파일이 바뀌면 자동으로 띄우고, [프로젝트 → 제외·알림]에서 더 추가할 수 있습니다.

### ③ 완료

패키지 폴더 경로가 보이고 **폴더 열기**, **보고서 열기**(`report.md` 를 ShipKit 안의 창으로)를 할 수 있습니다.

- 서버 연결을 등록한 프로젝트는 **서버에 바로 반영** 카드가 펼쳐집니다. → [4. 서버에 바로 반영](#4-서버에-바로-반영)
- 등록하지 않았으면 **직접 반영할 때** 카드에 서버에서 실행할 명령이 순서대로 나옵니다. 패키지 폴더를 서버에 올린 뒤 그대로 실행하면 됩니다. → [9. 서버에서 직접 실행할 때](#9-서버에서-직접-실행할-때)

**새 배포**를 누르면 처음으로 돌아갑니다.

## 4. 서버에 바로 반영

[프로젝트 → 서버 연결]에 서버를 등록하면, 완료 화면에서 WinSCP 나 터미널 없이 올리고 실행합니다. 서버를 고르면 올릴 위치·반영 경로·실행 계정이 한 줄로 보입니다.

| 버튼 | 하는 일 |
|---|---|
| **올리고 확인** | 패키지를 서버에 올린 뒤 `check` 를 실행합니다. 서버는 바뀌지 않습니다. 끝나면 로그 위에 결과 표가 생깁니다: apply 때 바뀌는 파일 수와, 신규·변경·동일·삭제예정·이미없음·정리예정별 파일 목록. |
| **백업 후 반영** | `backup` → `apply`. 바뀌거나 지워질 기존 파일을 먼저 백업하고 반영합니다. 실행 전에 확인을 받습니다. |
| **되돌리기** | `rollback`. 백업 기준으로 반영 전 상태로 복구합니다. 새로 추가됐던 파일과 apply 가 새로 만든 빈 폴더는 제거합니다. |
| **취소** | 진행 중일 때만 보입니다. 올리기·실행을 끊습니다. 서버에서 이미 시작된 명령은 끝까지 돌 수 있습니다. |

알아 둘 것:

- **처음 접속하는 서버**는 지문(host key)을 보여 주고 묻습니다. 맞으면 [예]. 기억해 두고 다음부터는 묻지 않으며, 지문이 바뀌면 접속하지 않습니다. 서버를 다시 설치해 지문이 바뀐 것이 맞으면 [프로젝트 → 서버 연결]의 **서버 지문 잊기**를 누르고 다시 접속합니다.
- **비밀번호**(접속·키 파일 암호·sudo/su)는 처음 접속할 때 묻습니다. 저장을 고르면 Windows 자격 증명 관리자에 넣어 다음부터 묻지 않습니다. 설정 파일에는 들어가지 않습니다. 로그인에 실패하면 저장한 값을 지우고 다음에 다시 묻습니다.
- **서버 명령(hooks)** 이 있으면 반영·되돌리기 전에 함께 실행할지 묻습니다. [아니요]를 누르면 파일만 반영합니다.
- 서버 출력이 **10분** 동안 없으면 네트워크가 끊긴 것으로 보고 저절로 중단합니다.
- 올리고 실행한 결과는 패키지에 남아 [기록]의 **서버 반영** 탭에서 보입니다.

## 5. 기록

이 프로젝트로 만든 패키지 목록입니다. MR 번호·제목·파일 경로로 찾을 수 있고, 패키지를 고르면 오른쪽에 자세한 내용이 보입니다.

| 탭 / 버튼 | 하는 일 |
|---|---|
| 위쪽 요청 목록 | 그때 고른 MR·PR. **열기**로 GitLab·GitHub 페이지를 엽니다. |
| **파일 / 서버 명령** 탭 | 들어간 파일, 함께 실행하는 서버 명령 |
| **서버 반영** 탭 | 화면에서 올리고 반영한 이력. 서버별로 "반영됨 / 되돌림" 배지가 붙습니다. |
| **폴더 열기 / 보고서 열기** | 패키지 폴더와 `report.md` |
| **같은 내용으로 다시 만들기** | 배포 화면에 같은 MR·파일을 채워 넣습니다. 지금 로컬 파일로 새 패키지를 만듭니다. |
| **서버 상태** (위쪽) | 서버의 배포 이력 파일을 읽어, 지금 어떤 패키지가 반영돼 있는지와 최근 이력을 보여 줍니다. |
| **서버에서 되돌리기** | 이 패키지가 반영돼 있는 서버에서 `rollback` 을 실행합니다. 여러 서버에 반영했으면 어느 서버인지 묻습니다. |

## 6. 프로젝트 설정

프로젝트는 왼쪽 위 프로젝트 목록의 **새 프로젝트 추가**로 추가합니다. 추가 창에서는 기본 항목만 넣고, 자세한 설정은 추가한 뒤 아래 탭에서 바꿉니다. 고친 값은 **저장**을 눌러야 반영되고, **되돌리기**는 저장 전 상태로 돌립니다.

**비워 둔 칸은 기본값을 따릅니다.** 흐린 글씨가 지금 쓰이는 값입니다. 저장소에 팀 공유 파일(`.shipkit.yml`)이 있으면 그 값도 함께 쓰며, 그런 항목에는 "…값을 따릅니다" 띠가 보입니다. 이 PC 에서만 다르게 쓰려면 띠의 **직접 지정**을 켜고 고칩니다. 파일의 우선순위는 [10. 설정 파일](#10-설정-파일)에 있습니다.

### 기본

| 항목 | 뜻 |
|---|---|
| 이름 | 목록에 보이는 이름. 패키지 경로의 `{project}` 로도 쓰입니다. |
| 로컬 경로 | 로컬 git 저장소 최상위 폴더 |
| 패키지 생성 경로 | 이 아래에 날짜 폴더로 패키지가 생깁니다. 비우면 [앱 설정]의 기본값. |
| 서버 OS | 리눅스(`shipkit.sh`) 또는 Windows(`shipkit.ps1`). |
| 서버 배포 경로 | 서버에서 이 프로젝트가 있는 폴더. Java 웹이면 `WEB-INF` 바로 위(예: `/app/tomcat/webapps/ROOT`), Windows 는 `D:/tomcat/webapps/ROOT` 처럼 `/` 로. |
| GitLab 프로젝트 | 프로젝트 ID 또는 `그룹/프로젝트` (예: `erp/web`) |
| GitHub 저장소 | `owner/name` |
| 패키지 폴더 이름 | 날짜 형식. 비우면 [앱 설정]의 기본값. |

**이 프로젝트 지우기**는 목록에서만 지웁니다. 로컬 저장소와 만든 패키지는 그대로 둡니다.

### 반영 규칙

**프리셋**은 언어·빌드 도구별로 미리 정한 규칙 묶음입니다. 맞는 것이 있으면 고르기만 하면 됩니다.

| 프리셋 | 방식 | 대상 |
|---|---|---|
| `maven` / `gradle` | changes | Java 웹. `.java` → 빌드된 `.class`(내부 클래스 포함), 리소스 → `WEB-INF/classes`, webapp → 루트 |
| `python` | changes | Django, Flask 등. 바뀐 소스 그대로. `__pycache__`·가상환경·테스트 제외 |
| `static` | changes | 정적 사이트, PHP, Node. 바뀐 파일 그대로. `node_modules` 제외 |
| `vite` / `vue-cli` | sync | Vue, React. `dist/` 전체 동기화, 옛 빌드 파일 정리 |

**방식** 두 가지:

- **변경 파일 매핑 (changes)**: 바뀐 파일만 규칙대로 서버 위치에 넣습니다. **반영 규칙** 표에서 저장소의 소스 폴더를 서버 배포 경로 아래 어디에 둘지 정합니다(`.` = 전체). **빌드 결과 폴더**를 적으면 `.java` 대신 그 폴더의 `.class` 를 넣습니다. 멀티 모듈이면 **모듈 폴더**에 `web, admin` 처럼 쉼표로 적습니다.
- **빌드 결과 동기화 (sync)**: 결과 파일 이름이 빌드마다 바뀌는 프로젝트용. **빌드 결과 폴더** 전체를 패키지에 담고, 서버에서는 내용이 다른 파일만 바꿉니다. **옛 파일 정리 폴더**는 이번 빌드에 없는 파일을 서버에서 지울 폴더입니다(쉼표로 여러 개). 파일 이름이 빌드마다 바뀌는 `assets/` 같은 폴더에 씁니다. 정리 폴더 밖(예: `uploads/`)은 건드리지 않습니다.

**경로 시험**: 파일 경로를 넣고 **시험**을 누르면 지금 규칙으로 서버 어디에 들어가는지 보여 줍니다. 저장하지 않은 값으로 시험하므로 규칙을 고치면서 확인할 수 있습니다. 앞에 `D` 와 탭을 붙이면 삭제로 봅니다.

### 서버 명령

배포할 때마다 서버에서 손으로 치던 명령(톰캣 재시작 등)을 적어 둡니다. 서버에서 `apply` 를 실행하면 파일 반영에 이어 이 명령도 실행합니다. **실행 전에 꼭 묻고, y 를 눌러야 실행합니다.** 없으면 비워 둡니다.

| 단계 | 언제 |
|---|---|
| 반영 전 (`pre_apply`) | 서버 파일을 바꾸기 전. 실패하면 파일을 바꾸지 않고 멈춥니다. 예: `sudo systemctl stop tomcat` |
| 반영 후 (`post_apply`) | 파일을 모두 바꾼 뒤. 가장 많이 쓰는 단계. 예: `sudo systemctl restart tomcat` |
| 되돌린 후 (`post_rollback`) | rollback 으로 이전 파일로 되돌린 뒤. 보통 "반영 후"와 같은 재시작 명령. |

**조건** 칸(선택)에 파일 패턴을 적으면 그 패턴에 맞는 파일이 바뀐 배포에만 명령을 넣습니다. 예를 들어 `**/*.java` 를 적으면 Java 소스가 바뀐 배포에서만 재시작하고, JSP·JS 만 바뀐 배포에서는 재시작하지 않습니다. 비워 두면 매번 넣습니다. Windows 서버의 명령은 PowerShell 명령입니다(예: `Restart-Service Tomcat9`).

**새로 생기는 파일의 소유자·권한** (리눅스 서버만): 배포로 서버에 처음 생기는 파일·폴더에만 적용합니다. 이미 있던 파일은 원래 소유자·권한을 그대로 둡니다. 비워 두면 apply 를 실행한 계정 소유가 되고 권한은 서버 기본값을 따릅니다. **배포 이력 파일**은 서버에 반영 기록을 남길 위치입니다(기본 `~/.shipkit/history.log`).

### 제외·알림

- **배포에서 뺄 파일**: 프리셋이 이미 빼는 파일에 더해집니다. 한 줄에 하나씩(예: `docs/**`, `**/*.bak`).
- **민감 파일**: `.env`, `*.pem`, `*.key`, `*.jks`, `id_rsa` 같은 파일은 기본으로 막습니다. **더 막기**에 패턴을 더하고, 꼭 배포해야 하는 파일은 **예외 허용**에 적습니다(예: `config/.env.dev`).
- **알림**: 이 패턴의 파일이 바뀌면 확인 화면과 보고서에 알림을 띄웁니다(예: DB 반영, 라이브러리 추가).

### 서버 연결

완료 화면에서 바로 올리고 반영할 서버입니다(SSH/SFTP). 개발·운영처럼 여러 대를 등록할 수 있습니다.

| 항목 | 뜻 |
|---|---|
| 이름 / 호스트 / 포트 / 접속 계정 | SSH 접속 정보 |
| 인증 | 비밀번호, 또는 SSH 키 파일(예: `C:/Users/me/.ssh/id_ed25519`). 암호가 있으면 접속할 때 묻습니다. |
| 올릴 위치 | 패키지 폴더를 올릴 곳(기본 `~/deploy`). 이 아래에 날짜 폴더로 올립니다. Windows 서버는 `~/deploy` 또는 `D:/deploy` 같은 절대 경로. |
| 실행 계정 | 접속하는 계정과 서버 스크립트를 실행할 계정이 다를 때 **다른 계정으로 실행**을 고릅니다(리눅스만). 전환 방법은 `sudo -u 계정` 또는 `su - 계정`. 이때 올릴 위치는 실행 계정도 들어갈 수 있는 폴더여야 합니다(예: 실행 계정의 홈 아래). |
| 실행할 때 비밀번호가 필요합니다 | sudo 는 접속 계정, su 는 실행 계정의 비밀번호를 묻습니다. 끄면 비밀번호 없이 실행하고, 서버가 비밀번호를 물으면 기다리지 않고 바로 실패합니다. |
| 올린 패키지 폴더의 소유자를 실행 계정으로 (chown) | 실행 계정이 패키지 폴더를 읽고 백업을 쓸 수 있게 합니다. |
| 서버 배포 경로 | 서버마다 다르면 따로. 비우면 프로젝트 값. |

**연결 시험**으로 접속만 확인할 수 있고, **저장된 비밀번호 지우기**로 이 서버의 비밀번호·키 암호를 자격 증명 관리자에서 지웁니다.

## 7. 연결

MR·PR 목록을 불러올 GitLab·GitHub 를 연결합니다.

- **GitLab**: 주소(예: `https://gitlab.example.com`)와 토큰. 토큰은 `read_api` 권한이면 됩니다.
- **GitHub**: github.com 이면 주소를 비웁니다. Enterprise 는 `https://<호스트>/api/v3`. 토큰은 저장소 읽기 권한이면 충분하고, 공개 저장소는 토큰 없이도 되지만 조회 한도가 작습니다.
- 토큰은 설정 파일이 아니라 **Windows 자격 증명 관리자**에 주소별로 저장됩니다. 주소를 바꾸면 **연결 저장**을 누른 뒤 토큰을 다시 저장하세요.

## 9. 서버에서 직접 실행할 때

서버 연결을 등록하지 않았거나 WinSCP 등으로 직접 올릴 때의 절차입니다. 패키지 폴더(날짜 폴더)를 통째로, 또는 tar.gz 로 서버에 올립니다. **서버 배포 경로 밖**(예: `~/deploy/2026-10-27-1530`)에 두고 그 폴더에서 실행합니다.

```bash
chmod +x shipkit.sh       # tar.gz 로 올렸다면 필요 없음 (bash shipkit.sh check 처럼 실행해도 됨)
./shipkit.sh check        # 신규/변경/동일/삭제예정/정리예정 확인 (서버 변경 없음)
./shipkit.sh backup       # 바뀌거나 지워질 기존 파일을 backup/ 에 보관
./shipkit.sh apply        # 반영 + 삭제 + 정리 (backup 없이는 실행되지 않음)
./shipkit.sh rollback     # backup 기준으로 원복
./shipkit.sh history      # 이 서버의 배포 이력 (최근 20건)
```

- `-y`: 서버 명령을 묻지 않고 실행(Jenkins 등 자동화용). `--no-hooks`: 서버 명령을 실행하지 않고 파일만.
- 서버와 내용이 같은 파일은 건드리지 않습니다. 한 번 만든 백업은 덮어쓰지 않습니다. WAS 재시작은 서버 명령에 적어야 합니다.
- 같은 대상에 다른 사람이 backup·apply·rollback 중이면 멈춥니다.
- 패키지의 `files/` 안이 서버 배포 경로 기준 그대로이므로, 스크립트 없이 WinSCP 로만 옮길 때는 `files/` 안의 내용만 복사하면 됩니다.

**Windows 서버** (서버 OS 를 Windows 로 둔 프로젝트)는 `shipkit.ps1` 이 들어갑니다. 기능은 같습니다.

```powershell
powershell -ExecutionPolicy Bypass -File .\shipkit.ps1 check
powershell -ExecutionPolicy Bypass -File .\shipkit.ps1 backup
powershell -ExecutionPolicy Bypass -File .\shipkit.ps1 apply      # -Yes / -NoHooks
powershell -ExecutionPolicy Bypass -File .\shipkit.ps1 rollback
```

메일이나 인터넷으로 받은 파일을 Windows 가 막으면 패키지 폴더에서 `Get-ChildItem -Recurse | Unblock-File` 을 실행하세요.

## 10. 설정 파일

| 파일 | 위치 | 담는 값 |
|---|---|---|
| 개인 설정 `shipkit.yaml` | 내 PC `%APPDATA%\shipkit\` | 로컬 경로, 패키지 생성 경로, GitLab·GitHub 주소 |
| 프로젝트 설정 `.shipkit.yml` | 프로젝트 저장소 루트(커밋) | 프리셋, 서버 경로, 서버 명령, 제외 규칙, 서버 연결 등 팀이 같이 쓰는 값 |

우선순위는 **개인 기본값 < `.shipkit.yml` < 개인 설정의 프로젝트 항목**입니다. 제외·알림·민감 파일 목록은 세 곳을 합칩니다. `.shipkit.yml` 에는 로컬 경로·패키지 생성 경로·토큰 같은 개인 값을 넣을 수 없습니다. 토큰과 비밀번호는 어느 파일에도 들어가지 않고 Windows 자격 증명 관리자에만 있습니다.

화면에서 저장하면 파일의 주석은 사라지고, 저장 직전 내용은 같은 폴더의 `.bak` 파일로 남습니다.

## 11. 문제가 생겼을 때

| 증상 | 확인할 것 |
|---|---|
| MR 목록이 안 불러와짐 | 점검 띠에 "GitLab 토큰 없음"이 있으면 [연결]에서 토큰 저장. 주소를 바꿨으면 토큰도 다시 저장. |
| "빌드 누락 의심" 경고 | 소스가 빌드 결과보다 새롭습니다. 다시 빌드한 뒤 **다음: 미리보기**. |
| "MR 커밋이 로컬에 없음" | 점검 띠의 **pull 받기** 또는 직접 pull 한 뒤 다시 빌드. |
| 패키지가 안 만들어짐 | 확인 단계에 실패 항목이 있습니다. 필터 **실패**로 원인을 보고 고치거나, 빼고 만들기를 고릅니다. |
| 서버 지문이 바뀌었다며 접속 안 됨 | 서버를 새로 설치했거나 다른 서버로 바뀐 경우입니다. 관리자에게 확인한 뒤 [프로젝트 → 서버 연결]의 **서버 지문 잊기**를 누르면 다음 접속 때 다시 묻습니다. |
| 비밀번호를 저장했는데 다시 물음 | 로그인 실패 시 저장한 값을 지웁니다. 새 비밀번호를 넣고 다시 저장하세요. |
| 서버 명령 실행 중 멈춤 | 비밀번호 없이 실행하도록 해 둔 sudo/su 가 비밀번호를 묻는 경우입니다. [서버 연결]에서 "실행할 때 비밀번호가 필요합니다"를 켜세요. |
| 반영 중 10분 넘게 출력 없음 | 네트워크가 끊긴 것으로 보고 중단합니다. [기록 → 서버 상태]로 서버가 어디까지 했는지 확인하세요. |
| 되돌리고 싶음 | [기록]에서 패키지를 고르고 **서버에서 되돌리기**. 직접 올렸다면 패키지 폴더에서 `./shipkit.sh rollback`. |
| "예상하지 못한 오류" 창이 뜸 | 프로그램 문제입니다. 앱 설정 → 정보 → **로그 파일 열기**의 `shipkit.log` 와 오류 직전에 한 일을 담당자에게 알려 주세요. |
